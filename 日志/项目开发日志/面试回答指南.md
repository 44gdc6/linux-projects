## 一、项目经历

### 1.1 项目概述

**Q：介绍一下你的项目**

> 我做的是一套危险品运输车辆的安全监测系统，硬件上以 i.MX6ULL 为主控运行 Linux，通过 CAN 总线挂载 STM32 节点采集传感器数据；软件上用 LVGL 做本地界面，MQTT 连接 OneNET 云平台，SQLite 存储历史记录。
>
> 我主要负责驱动开发、CAN 通信协议、业务逻辑和云端对接。

**知识点：**

```
i.MX6ULL: NXP 出品的 ARM Cortex-A7 处理器，主频 528MHz，常用于嵌入式 Linux
STM32: ST 出品的 Cortex-M 系列 MCU，适合做传感器采集节点
CAN 总线: 一种串行通信协议，抗干扰能力强，适合工业/车载场景

**追问：** 项目的技术难点是什么？

> 有三个难点：
> 1. DHT11 时序——Linux 下很难做到 us 级精确时序，最终用 hrtimer 高精度定时器解决

> 3. 实时性——多线程轮询效率低，后来改成中断驱动 + 环形缓冲

### 1.2 驱动层深挖

**Q：MPU6050 驱动怎么实现的？**

> MPU6050 是一个六轴 IMU，通过 I2C 连接 i.MX6ULL。我用 misc 设备框架实现，设备节点是 `/dev/mpu6050_misc`。
>
> 驱动流程：
> 1. 设备树配置 compatible 和 I2C 地址 0x68
> 2. probe 函数里先读 WHO_AM_I 寄存器验证设备存在
> 3. misc_register 注册字符设备
> 4. read 函数用 `i2c_smbus_read_i2c_block_data()` 一次读 14 字节，包含加速度和陀螺仪数据
> 5. 用 copy_to_user 返回给应用层

**知识点：**

```
misc 设备: Linux 内核提供的简化字符设备框架，自动分配 minor 号
- miscdevice 结构体包含 minor、name、fops
- misc_register() 自动创建 /dev/xxx

I2C block read:
- 一次传输读取多个字节，减少总线开销
- 使用 repeated start 时序（不发停止位直接发起新起始）
- 比逐字节 read 快约 5-6 倍

寄存器布局:
- 0x3B-0x40: 加速度 xyz（各 2 字节，高字节在前）
- 0x43-0x48: 陀螺仪 xyz（各 2 字节）
- 0x75: WHO_AM_I（应返回 0x68）
```

**追问：** 设备树里 MPU6050 配置了什么？

```dts
&i2c1 {
    mpu6050@68 {
        compatible = "invensense,mpu6050";
        reg = <0x68>;                    // I2C 从机地址
        interrupt-parent = <&gpio1>;     // 中断引脚
        interrupts = <18 IRQ_TYPE_EDGE_RISING>;
    };
};
```

**追问：** KO 代码怎么写的？

> 参考内核 drivers/misc/ 下的示例驱动和社区文档，根据硬件手册和项目需求定制。核心结构：
> - `module_init` / `module_exit`：模块加载卸载入口
> - `i2c_driver` 结构体：包含 probe/remove 和 id_table
> - `file_operations`：实现 open/read/write/ioctl
> - `module_i2c_driver()` 宏：自动展开为注册代码

**Q：DHT11 驱动怎么做？时序怎么完成？**

> DHT11 是单总线协议，时序非常严格，这是整个项目最大的难点。
>
> 时序流程：
> 1. 主机拉低 GPIO 18ms+ 发起启动信号
> 2. 拉高 20-40us，等待 DHT11 响应
> 3. DHT11 拉低 80us + 拉高 80us 表示响应
> 4. 每个 bit 用高电平持续时间区分：26-28us 是 0，70us 是 1
> 5. 共接收 40 bit = 5 字节（湿度+温度+校验）
>
> Linux 下的实现难点：
> - 用户态 usleep 精度不够（通常只有 ms 级）
> - 中断上下文不能做长时间操作
>
> 我的方案是用 hrtimer（高精度定时器）+ GPIO 中断：
> - 配置 GPIO 为中断输入
> - 每次上升沿触发中断，用 hrtimer 记录时间戳
> - 通过两次中断的时间差判断是 0 还是 1

**知识点：**

```
hrtimer (High Resolution Timer):
- 精度达到纳秒级（vs 普通 timer 仅毫秒级）
- 基于硬件时钟源（如 ARM 的 generic timer）
- API: hrtimer_init() → hrtimer_start() → 回调函数

GPIO 模拟单总线时序:
1. gpio_direction_output() 设为输出
2. gpio_set_value(0) 拉低
3. usleep_range(18000, 20000) 等待 18ms
4. gpio_set_value(1) 拉高
5. gpio_direction_input() 切换为输入
6. request_irq() 注册中断，捕获响应

校验字节验证:
前 4 字节累加，低 8 位应等于第 5 字节
if ((buf[0] + buf[1] + buf[2] + buf[3]) == buf[4])
    // 校验通过
```

**追问：** 为什么不用 usleep？

> usleep 是基于 jiffies 的粗粒度定时，最小精度通常是 1ms（HZ=1000），而且可能被高优先级任务调度打断。DHT11 的时序要求 us 级精度，必须用 hrtimer。

**Q：MQ-3 ADC 驱动怎么做？**

> MQ-3 是酒精传感器，输出模拟电压。我用 Linux IIO（Industrial IIO）框架实现。
>
> 实现方式：
> 1. 设备树配置 ADC 通道
> 2. 驱动中用 `iio_channel_get()` 获取通道
> 3. `iio_read_channel_raw()` 读取原始 ADC 值
> 4. 转换为电压值：voltage = reference_voltage * raw_value / 4096（12 位 ADC）
> 5. 注册 misc 设备，read() 返回 ADC 值

**知识点：**

```
IIO 框架:
- Linux 标准的 ADC/传感器子系统
- 提供统一接口，支持多通道、触发、缓冲
- 核心 API:
  iio_channel_get()       获取通道
  iio_read_channel_raw()  读取原始值
  iio_channel_release()   释放通道

ADC 精度:
- 12 位 ADC = 4096 级
- 分辨率 = 参考电压 / 4096
- 例如 3.3V 参考电压 → 分辨率约 0.8mV
```

### 1.3 CAN 通信深挖

**Q：CAN 总线架构是怎样的？**

> 我的设计是主站轮询模式：
> - i.MX6ULL 做主站，STM32F407/F103 做从站
> - 帧 ID 分配：心跳 0x100+、命令 0x300+、应答 0x200+
> - 波特率 500kbps，CAN 2.0A 标准帧
>
> 通信流程：
> 1. 主站发送命令帧（如读取传感器数据）
> 2. 从站收到后返回应答帧
> 3. 从站每秒发送一次心跳帧
> 4. 主站检测心跳超时判断节点是否在线

**知识点：**

```
帧 ID 分配规则:
| 帧类型 | ID 范围     | 方向    |
|--------|------------|---------|
| 心跳帧 | 0x100+node | 从→主   |
| 应答帧 | 0x200+node | 从→主   |
| 命令帧 | 0x300+node | 主→从   |

节点 ID:
- F103: 0x01
- F407: 0x02

数据域格式（8 字节）:
- 心跳: [status, 0, 0, 0, 0, 0, 0, counter]
- 命令: [cmd, param1, param2, 0, 0, 0, 0, 0]
- 应答: [cmd, status, data1, data2, data3, data4, 0, 0]
```

**追问：** 怎么验证协议一致性？

> 我写了 Python 契约测试，做源码级验证：
> - 解析 STM32 的 C 源码，提取帧 ID 和数据格式定义
> - 自动生成测试用例，验证帧 ID 范围是否正确
> - 验证数据域长度是否为 8 字节
> - 验证心跳间隔是否稳定在 1 秒

## 二、I2C 总线

**Q：I2C 有几根线？起始信号时序？**

> I2C 有两根线：SDA（数据线）和 SCL（时钟线），都是开漏结构，需要上拉电阻。
>
> 起始信号：SCL 保持高电平期间，SDA 从高变低。
>
> ```
> SCL: ___|‾‾‾|___|‾‾‾|___
> SDA: ‾‾‾‾‾‾\_____|‾‾‾‾‾‾
>       起始条件
> ```

**知识点：**

```
I2C 基础:
- 开漏结构: 只能主动拉低，不能主动拉高，需要外部上拉电阻（通常 4.7kΩ）
- 7 位地址: 范围 0x03-0x77（0x00-0x02 和 0x78-0x7F 保留）
- 速率: 标准 100kHz、快速 400kHz、高速 3.4MHz

时序:
起始: SCL=HIGH 时，SDA ↓
停止: SCL=HIGH 时，SDA ↑
ACK:  第 9 个时钟，接收方拉低 SDA
NACK: 第 9 个时钟，SDA 保持高

repeated start:
- 不发停止位，直接发新的起始信号
- 用于连续读取（如 block read）
- 避免总线被其他主机抢占
```

**追问：** I2C 总线仲裁机制？

> 多主机时，每个主机在发送数据的同时监听总线电平。
> 如果发送隐性(1)但检测到显性(0)，说明有更高优先级的主机在发送，自动退出仲裁。
> ID 值越小优先级越高（0 比 1 优先）。

## 三、SPI 总线

**Q：SPI 有几根线？**

> 4 根线：MOSI（主出从入）、MISO（主入从出）、SCLK（时钟）、CS（片选）。
> 全双工，速度比 I2C 快很多。

**知识点：**

```
SPI 四种模式（CPOL/CPHA 组合）:
| 模式 | CPOL | CPHA | 空闲电平 | 采样边沿 |
|------|------|------|---------|---------|
| 0    | 0    | 0    | LOW     | 上升沿  |
| 1    | 0    | 1    | LOW     | 下降沿  |
| 2    | 1    | 0    | HIGH    | 下降沿  |
| 3    | 1    | 1    | HIGH    | 上升沿  |

SPI vs I2C:
| 特性 | SPI | I2C |
|------|-----|-----|
| 线数 | 4 根 | 2 根 |
| 速度 | 最高 100MHz+ | 最高 3.4MHz |
| 双工 | 全双工 | 半双工 |
| 片选 | 硬件 CS 线 | 软件地址寻址 |
| 复杂度 | 简单 | 较复杂 |
```

## 四、CAN 总线

**Q：CAN 总线仲裁机制？**

> CAN 采用非破坏性仲裁：
> 1. 多个节点同时发送时，逐位比较 ID
> 2. 显性电平(0) 覆盖隐性电平(1)
> 3. ID 值越小优先级越高
> 4. 仲裁失败的节点自动退出，等待总线空闲后重发

**示例：**

```
节点A 发送 ID=0x101 (0001 0000 0001)
节点B 发送 ID=0x102 (0001 0000 0010)
                ↓
第 11 位：A 发 0（显性），B 发 1（隐性）
                ↓
B 检测到总线电平与自己不同，仲裁失败，退出发送
A 继续发送，不被打断
```

**知识点：**

```
CAN 总线基础:
- 差分信号: CAN_H 和 CAN_L，抗干扰能力强
- 终端电阻: 120Ω，匹配阻抗，减少信号反射
- 最大距离: 40m@1Mbps，1000m@50kbps

帧格式:
标准帧: 11 位 ID + 8 字节数据
扩展帧: 29 位 ID + 8 字节数据

错误处理:
- 位错误: 发送方监听总线，发现与自己不同
- 填充错误: 连续 6 个相同电平
- CRC 错误: 校验失败
- 格式错误: 固定格式位不正确
- ACK 错误: 无节点应答

Bus-Off:
- 发送错误计数器 > 255 时进入
- 节点自动退出总线
- 需要软件恢复（重新初始化）
```

**追问：** 终端电阻为什么要 120Ω？

> CAN 总线使用双绞线传输差分信号，线缆有特征阻抗（约 120Ω）。终端电阻匹配阻抗，吸收反射波，避免信号在总线两端来回反射导致通信失败。

## 五、中断机制

**Q：中断上半部能调用 I2C 函数吗？为什么？**

> 不能。I2C 操作涉及总线时序，可能睡眠等待从设备响应。中断上下文不能睡眠，否则会导致系统崩溃。

**知识点：**

```
中断上下文限制:
- 不能睡眠（不能调用 mutex_lock、kmalloc(GFP_KERNEL) 等可能睡眠的函数）
- 不能调度其他进程
- 不能访问用户态地址空间
- 必须尽快执行完毕

中断上半部 vs 下半部:
| 特性 | 上半部 | 下半部 |
|------|--------|--------|
| 执行环境 | 中断上下文 | 进程上下文 |
| 能否睡眠 | 不能 | 可以 |
| 延迟 | 立即执行 | 延后执行 |
| 用途 | 快速响应 | 耗时操作 |
| 实现 | irq_handler | tasklet/workqueue/threaded_irq |

自旋锁 vs 互斥锁:
| 特性 | 自旋锁 spin_lock | 互斥锁 mutex |
|------|------------------|-------------|
| 等待方式 | 忙等待（循环检查） | 睡眠等待 |
| 中断上下文 | ✅ 可以用 | ❌ 不能用 |
| 持有时间 | 应尽量短 | 可以较长 |
| 适用场景 | 中断/原子操作 | 进程上下文 |
```

**追问：** 中断上半部可以用自旋锁吗？

> 可以。自旋锁不会睡眠，适合中断上下文。典型用法是 `spin_lock_irqsave()`，它会保存当前中断状态并关闭本地中断，防止中断重入。

## 六、C 语言基础

**Q：int 在 32 位和 64 位系统各占多少字节？**

> **都是 4 字节。** 这是 C 语言标准规定的。long 在 64 位系统才是 8 字节。

**知识点：**

```
数据类型大小（x86/x64 Linux）:
| 类型     | 32 位 | 64 位 |
|----------|-------|-------|
| char     | 1     | 1     |
| short    | 2     | 2     |
| int      | 4     | 4     |
| long     | 4     | 8     |
|指针      | 4     | 8     |

大端 vs 小端:
大端: 高字节在低地址（网络字节序）
小端: 低字节在低地址（x86/x64）

验证方法:
// 方法 1: union
union { int i; char c; } test = {1};
printf("%s\n", test.c == 1 ? "小端" : "大端");

// 方法 2: 指针
int i = 1;
printf("%s\n", *(char*)&i == 1 ? "小端" : "大端");
```

**Q：第 10 位置 1，怎么实现？**

> 用按位或：`val |= (1 << 10)`
>
> 置 0 用：`val &= ~(1 << 10)`
>
> 翻转用：`val ^= (1 << 10)`

**知识点：**

```
位操作:
置 1: val |= (1 << n)
置 0: val &= ~(1 << n)
翻转: val ^= (1 << n)
判断: val & (1 << n)  // 非零则为 1

注意: 不能用异或置 1，异或是翻转，不是置位
```

**Q：数组能从函数返回吗？**

> 不能直接返回局部数组。函数返回后局部变量被销毁，数组内存失效。
>
> 三种替代方案：
> 1. static 数组（生命周期延长到程序结束，但非线程安全）
> 2. malloc 动态分配（需要调用方 free）
> 3. 通过参数传入（最常用）

**Q：const 和 #define 区别？**

> 1. const 有类型检查，#define 只是简单文本替换
> 2. const 有作用域，#define 从定义到文件末尾
> 3. const 调试时可见，#define 在预编译阶段就被替换
> 4. #define 可以定义宏函数，const 不行

## 七、内核基础

**Q：Linux 启动流程？**

> 1. **Bootloader（U-Boot）**：初始化硬件，加载内核镜像
> 2. **内核初始化**：start_kernel() → 解析设备树 → 初始化各子系统
> 3. **挂载根文件系统**：从 SD/eMMC 挂载 rootfs
> 4. **启动 init 进程**：PID=1，启动用户空间服务
> 5. **用户空间**：启动应用层程序

**知识点：**

```
内核启动关键函数:
start_kernel()          → 内核入口
setup_arch()            → 架构初始化，解析设备树
do_initcalls()          → 执行各子系统初始化
rest_init()             → 创建 init 和 kthreadd 进程

设备树解析:
of_platform_populate()  → 遍历设备树节点
of_match_device()       → 通过 compatible 匹配驱动
driver_probe_device()   → 调用驱动 probe 函数
```

**Q：死锁是什么？怎么避免？**

> 死锁是多个线程互相等待对方持有的锁，导致永远阻塞。
>
> 四个必要条件：
> 1. 互斥：资源一次只能被一个线程持有
> 2. 持有并等待：线程持有资源的同时等待其他资源
> 3. 不可抢占：不能强制释放线程持有的锁
> 4. 循环等待：线程之间形成等待环路
>
> 避免方法：
> - 固定加锁顺序
> - 使用超时（try_lock）
> - 减少锁的粒度
> - 避免嵌套锁

## 八、网络编程

**Q：TCP 三次握手？**

> 1. 客户端 → 服务器：SYN（我想连接）
> 2. 服务器 → 客户端：SYN+ACK（好的，我也准备好了）
> 3. 客户端 → 服务器：ACK（确认，开始传数据）

**知识点：**

```
三次握手原因:
- 防止历史连接：旧的 SYN 包到达服务器，服务器回复后客户端丢弃
- 同步序列号：双方确认初始序列号（ISN）
- 防止资源浪费：两次握手会导致服务器提前分配资源

四次挥手:
1. 客户端 → FIN（我发完了）
2. 服务器 → ACK（知道了，但我可能还没发完）
3. 服务器 → FIN（我也发完了）
4. 客户端 → ACK（好的，确认关闭）
→ 客户端等待 2MSL 后关闭（确保 ACK 被收到）

为什么挥手是四次:
- TCP 是全双工，每个方向独立关闭
- 服务器收到 FIN 时可能还有数据要发
- 所以 ACK 和 FIN 分开发送
```

**Q：MQTT 是什么？**

> MQTT 是轻量级的消息协议，基于发布/订阅模式。适合嵌入式设备和物联网场景。
>
> 核心概念：
> - Broker：消息服务器（如 OneNET）
> - Topic：消息主题（如 `/sensor/temp`）
> - QoS：服务质量等级（0/1/2）

**知识点：**

```
MQTT QoS 等级:
| QoS | 名称 | 说明 | 适用场景 |
|-----|------|------|---------|
| 0   | 最多一次 | 可能丢失 | 温度上报 |
| 1   | 至少一次 | 可能重复 | 告警通知 |
| 2   | 恰好一次 | 不丢不重 | 控制指令 |

心跳机制:
- keepalive: 客户端配置的心跳间隔
- 超时: 1.5 × keepalive 未收到消息则断开
- PINGREQ/PINGRESP: 心跳包
```

## 十、SQLite

**Q：为什么选 SQLite？怎么优化？**

> SQLite 是嵌入式数据库，零配置、单文件、跨平台，适合我的场景。
>
> 优化方法：
> 1. 事务批量插入：1000 条数据用一个事务，比逐条插入快 100 倍
> 2. WAL 模式：允许读写并发
> 3. 合理建索引：频繁查询的字段加索引
> 4. 定期清理：DELETE 旧数据后 VACUUM 压缩

**知识点：**

```
SQLite 特性:
- 零配置: 无需安装/启动服务
- 单文件: 整个数据库一个 .db 文件
- ACID: 支持事务
- 并发: 读并发，写串行（文件锁）

WAL (Write-Ahead Logging):
- 写操作先写日志，再写数据库
- 读操作不阻塞写操作
- 比默认的 DELETE 模式快 2-5 倍
```

## 十一、调试能力

**Q：驱动调试方法？**

> 1. **printk / dev_dbg**：最基础的内核打印
> 2. **ftrace**：跟踪函数调用和延迟
> 3. **strace**：跟踪用户态系统调用
> 4. **I2C 工具**：i2cdetect 扫描总线，i2cget/i2cset 读写寄存器
> 5. **CAN 工具**：candump 抓包，cansend 发送
> 6. **Oops 分析**：查看 PC 指针和调用栈，用 addr2line 定位源码

**知识点：**

```
内核调试工具:
| 工具 | 用途 | 示例 |
|------|------|------|
| printk | 打印日志 | pr_info("value=%d\n", val) |
| dev_dbg | 设备专用日志 | dev_dbg(&dev, "read ok\n") |
| ftrace | 函数跟踪 | echo function > current_tracer |
| kdump | 内核崩溃转储 | /proc/vmcore |
| gdb + kgdb | 内核远程调试 | 需要两台机器串口连接 |

I2C 调试:
i2cdetect -y 1           # 扫描 I2C 总线 1 上的设备
i2cget -y 1 0x68 0x75    # 从地址 0x68 的 0x75 寄存器读取
i2cset -y 1 0x68 0x6B 0x00  # 向寄存器写入值

Oops 分析:
1. 复制 Oops 信息
2. 提取 PC 指针（如 PC is at sensor_read+0x34/0x100）
3. addr2line -e sensor_drv.ko 0x34  # 定位源码行号
```

**Q：Oops 错误怎么分析？**

> 1. 找到 PC 指针（出错时执行的地址）
> 2. 看调用栈（backtrace），了解调用链
> 3. 用 addr2line 或 objdump 定位源码行号
> 4. 常见原因：空指针、越界访问、并发问题、栈溢出

## 十二、软实力

**Q：为什么选驱动开发？**

> 我对底层原理很感兴趣，喜欢理解硬件是怎么工作的。做驱动开发能让我从寄存器级别理解整个系统，而不仅仅是调用 API。在项目中解决 DHT11 时序问题的过程让我体会到驱动开发的挑战和成就感。

**Q：遇到过什么困难？怎么解决的？**

> DHT11 时序问题。最初用 usleep 延时，发现数据经常校验失败。后来查资料发现 Linux 用户态 usleep 精度不够，于是研究了 hrtimer 高精度定时器，结合 GPIO 中断捕获来测量高电平持续时间。调试了两天，用逻辑分析仪对比波形，最终解决了。
